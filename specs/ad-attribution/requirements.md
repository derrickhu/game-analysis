# 广告归因系统需求

## 背景

当前经分平台已经能按游戏统计新增、留存、LTV、广告收益和投放成本，但投放数据主要停留在自然日维度，无法把一个用户后续的深层行为归因到具体 campaign / adgroup / creative。发行优化需要从“今天花了多少钱、来了多少人”升级到“哪个素材带来的用户更能完成新手、留存、看广告和贡献 LTV”。

## 范围

- 首期接入花花妙屋，系统设计必须支持后续复用到别捞水果、灵宠消消塔等游戏。
- 先实现归因采集、归因解析、归因看板和回传 dry-run。
- 真实广告平台回传通过队列与 adapter 控制，先审计后开启。

## 用户故事

1. 作为发行负责人，我希望知道新用户来自哪个 campaign / adgroup / creative，以便判断素材和计划质量。
2. 作为投放优化人员，我希望按投放维度查看 D1/D3/D7 留存、LTV、教程完成和广告变现，以便把预算给到高质量来源。
3. 作为工程人员，我希望能在微信开发者工具里用 mock query 验证归因链路，也能在真实小预算广告里观察平台实际透传字段。
4. 作为数据负责人，我希望归因规则可追溯、可重算，并且回传广告平台前可 dry-run 审计。

## 验收标准

- 当小游戏通过带 `campaign_id` / `adgroup_id` / `creative_id` / `click_id` 的 query 启动时，系统应记录 `attribution_touchpoint` 事件。
- 当 SDK 设置公共归因参数后，系统应在后续事件参数中自动携带这些字段，且事件级参数可覆盖公共参数。
- 当用户首次被识别时，系统应把 `user_key` 绑定到首个有效触点，不因后续普通启动覆盖 acquisition 归因。
- 当没有有效触点时，系统应把用户标记为 `organic` 或 `unknown`，不得强行分配到付费渠道。
- 当归因回算执行后，系统应能按 campaign / adgroup / creative 输出新增、留存、LTV、广告收入和关键深层事件指标。
- 当深层事件满足回传规则时，系统应写入 `postback_queue`，并通过 dry-run 展示 payload、dedupe key、匹配归因和状态，不默认真实发送。
- 当在微信开发者工具中使用 mock query 启动时，调试页应能查询到对应事件、归因结果和回传候选。

## 非目标

- 首期不保证腾讯广告真实点击一定透传某个固定字段；真实字段需要小预算广告探针验证。
- 首期不做 SKAN 用户级归因合并。
- 首期不直接开启真实广告平台回传。
- 首期不引入第三方 MMP SDK。
